# 設計思想

hbg が何を守ろうとしているかです。ここを外すと、あとの判断が読み解けません。

どれも、実際に起きていた不具合から来ています。抽象的な理想ではなく、
「これをやらなかったせいでこうなった」という記録です。

## 1. 黙って別のやり方に落とさない

**できないことは、できないと言う。** 利用者が指定したことを、
勝手に別のもので代用しません。

### 実際にどうなっているか

`--checksum` は、両側に共通して使えるハッシュがなければ**起動時に失敗**します。

```go
// transfer/compare.go
if policy.uses(CompareHash) {
    ht, ok := commonHash(src, dst)
    if !ok {
        return nil, fmt.Errorf(
            "%s と %s の間に共通して使えるハッシュがありません。..." )
    }
}
```

黙ってサイズ比較に落とすと、利用者は「検証したつもりで検証されていない」
状態に置かれます。バックアップの道具でこれをやると、気づけません。

同じ考えで:

- 更新時刻を保持できないストレージへ、時刻での比較を指定したら起動時に断る
- OneDrive は quickXorHash を計算できないので、`Features.Hashes` を空にする
  （照合用の値を持っておらず、正しいと確かめられないため）
- S3 で分割送信されたオブジェクトの MD5 が分からないとき、ETag を
  MD5 として扱わない

### なぜそうするか

以前の hbg は、Dropbox へ書き込むとき全経路が `io.LimitReader(data, 150MiB)`
を通っていました。サイズが過小に伝わると、先頭だけが送られて**成功として
報告**されていました。バックアップが取れているつもりで中身が消えている、
という状態が起こりえたわけです。

「たぶん大丈夫だろう」で進める作りは、こういう形で牙をむきます。

## 2. 宣言されたサイズを信用しない

`Put` に渡される `meta.Size` は目安でしかありません。
実装は**読み終わるまで**を書き込みます。

```go
// storage/storage.go
// Put は path に r の内容を書き込みます。
//
//   - meta.Size は SizeUnknown のことがあります。
//     宣言されたサイズではなく、読み終わるまでを書き込んでください。
```

さらに、`storage.Copy` は転送後に**必ずサイズを検査**します。

```go
if info.Size != SizeUnknown && written.Size != SizeUnknown && written.Size != info.Size {
    return nil, fmt.Errorf("転送したサイズが一致しません（元 %d バイト、先 %d バイト）...")
}
```

`SizeUnknown`（-1）という値があるのは、**0（空ファイル）と「分からない」を
区別する**ためです。Google Drive のネイティブ形式はサイズを持たないので、
0 として扱うと空のファイルが黙って作られます。

## 3. 中身の欠けたファイルを残さない

書き込みは別名（`.名前.hbgpart`）で行い、書き終えてから本来の名前に
置き換えます。途中で止めても、本来の場所には中途半端なものが残りません。

| ストレージ | 置き換えの手段 |
| --- | --- |
| ローカル | `os.Rename` |
| SFTP | `posix-rename@openssh.com`（なければ削除してから改名） |
| SMB / FTP | 削除してから改名 |
| WebDAV | `MOVE`（Overwrite: T） |
| Dropbox / Drive / OneDrive / S3 | 書き込みが完了してはじめて見えるので、そのまま |

書きかけのものは一覧に出しません。別のところで走っている転送の
邪魔をしないためでもあります。

## 4. 失敗は分類してから扱う

バックエンドは失敗を `storage.Class` に分類して返します。
転送エンジンは `errors.As` だけを見ればよく、SDK ごとのエラー型を
知る必要がありません。

待っても直らないもの（存在しない・権限がない）を3回×5秒待って諦めたり、
一時的なものを1回で諦めたりしないためです。

詳しくは [error-handling.md](error-handling.md) を見てください。

## 5. 使うまで組み立てない

設定に書いてあるだけのストレージは、接続も認証もしません。

```console
hbg ls local:.        # Dropbox の認証は走らない
```

以前はどのコマンドでも設定にあるすべてのストレージを構築していたため、
ローカルのファイルを一覧するだけでクラウドの認証が走っていました。

`backend.Resolver` は名前の重複と知らない種別だけを起動時に検査し、
実際の組み立ては `Get(ctx, name)` まで遅らせます。

## 6. 取り返しのつかない操作は、迷ったらやらない

`sync --delete` は次の場合に削除しません。

- 転送に1件でも失敗があったとき。コピー元を読めなかっただけで
  「向こうには無い」と判断すると、取っておきたいものを消すことになります。
- `--include` や `--exclude` で対象外にしたもの。転送していないものを
  消すのは筋が通りません。

コピー元にないディレクトリは、まるごと消さずに中をたどって1件ずつ
控えます。まるごと消すほうが要求は少ないのですが、それだと絞り込みで
守ったはずのものまで巻き込みます。

## 7. 足すときに触る場所を減らす

新しいストレージを足すとき、触るのは2か所だけです。

1. `backend/<名前>/` を作る
2. `internal/cli/cmd.go` に blank import を1行足す

ヘルプの一覧も、設定ファイルの雛形も、登録された内容から組み立てます。

以前は種別ごとに6か所を触る必要がありました。その結果、実装が削除された
あとも `copy --help` が `ftp` を案内し続ける、ということが起きていました。
**嘘をつく余地を構造的に消す**のが狙いです。

## 8. 直した不具合には回帰試験を書く

判断の表は、そのまま表としてテストに書き下しています。

```go
// transfer/compare_test.go
{"コピー先のほうが新しく、サイズも違う（--update）", ...}
```

「なぜこの順序なのか」がコードから読み取れない判断は、テストの名前で
残しています。たとえば、更新時刻の判断をサイズの比較より先に行うのは、
`--update` を指定していてもサイズが違えば新しいファイルが古いもので
上書きされていたためです。
